# Documentation Design Knowledge

*On 5/8/2026 I asked ChatGPT 5.5 Thinking about the “meta” knowledge for writing technical documentation. This page has the important parts of the answer.*

---

What you’re asking about is usually called the **body of knowledge** for technical communication, documentation, instructional design, or education.

A good phrase would be:

> **Documentation requires domain knowledge, but creating documentation requires a body of knowledge in technical communication, information design, instructional design, and learning theory.**
> 

## The main fields

| Field | What it contributes |
| --- | --- |
| **Technical communication** | How to explain complex information clearly to specific audiences. This is the core field behind technical writing. |
| **Information architecture** | How to organize, structure, label, and connect information so users can find and understand it. |
| **Instructional design** | How to design learning experiences, tutorials, training, courses, and guided progression. |
| **Learning theory / pedagogy / andragogy** | How people learn; pedagogy is often about teaching in general, and andragogy is specifically adult learning. |
| **Content strategy** | How documentation fits business goals, product goals, governance, lifecycle, ownership, and publishing workflows. |
| **UX writing / content design** | How words guide users inside interfaces, flows, onboarding, forms, errors, and help systems. |
| **Rhetoric and audience analysis** | How purpose, audience, context, and persuasion shape communication. |
| **Documentation engineering** | Tooling, docs-as-code, versioning, publishing pipelines, structured content, reuse, localization, etc. |

The term **Technical Communication Body of Knowledge** is actually used directly by TCBOK, which describes the field as covering writing/editing, information architecture, content strategy, usability, accessibility, and project management. (TCBOK)

## What the “syllabus” looks like

A university-style technical writing / technical communication curriculum typically includes things like:

| Course area | Typical topics |
| --- | --- |
| **Audience and task analysis** | Who the reader is, what they are trying to do, what they already know, what they need next. |
| **Genres of technical communication** | User guides, API docs, tutorials, reference docs, release notes, proposals, reports, white papers, SOPs. |
| **Clear technical prose** | Concision, plain language, definitions, examples, warnings, procedures, consistency. |
| **Document design** | Headings, layout, hierarchy, tables, callouts, diagrams, typography, visual emphasis. |
| **Information architecture** | Navigation, taxonomies, topic types, metadata, search, findability. |
| **Procedural writing** | Step-by-step tasks, prerequisites, expected results, troubleshooting, decision paths. |
| **Instructional design** | Learning objectives, sequencing, exercises, assessment, feedback, training design. |
| **Usability testing** | Testing whether users can actually complete tasks using the docs. |
| **Accessibility** | Writing and structuring content for people using assistive technologies. |
| **Tools and publishing** | Markdown, HTML, CMSs, docs-as-code, Git, static site generators, help-authoring tools. |
| **Editing and style systems** | Style guides, terminology control, voice/tone, grammar, consistency. |
| **Project and content lifecycle** | Planning, reviews, SMEs, versioning, governance, maintenance. |

For example, Utah Valley University’s Technical Communication minor lists outcomes such as producing workplace technical communication genres, explaining complex technical information clearly, collaborating on deliverables, improving user experience, and designing document interfaces using usability and graphic design principles. (Utah Valley University Academic Catalog) Spokane Falls’ technical writing outcomes similarly include explaining specialized information to non-specialists, using discipline-specific formats, assessing source validity, and applying information design. (catalog.spokane.edu)

## If the role is “educator” rather than “tech writer”

Then the meta-field shifts more toward **instructional design** and **learning science**.

A syllabus there often includes:

| Area | Typical topics |
| --- | --- |
| **Learning objectives** | Defining what learners should be able to do. |
| **Bloom’s Taxonomy** | Moving from remembering and understanding toward applying, analyzing, evaluating, and creating. |
| **ADDIE** | Analysis, Design, Development, Implementation, Evaluation. |
| **Gagné’s Nine Events** | A structured model for lesson/training design. |
| **Assessment design** | How to know whether learning happened. |
| **Cognitive load** | Avoiding overload; sequencing material so it can be absorbed. |
| **Scaffolding** | Supporting learners early, then gradually removing support. |
| **Practice and feedback** | Designing exercises, labs, checks, and reinforcement. |
| **Adult learning** | Relevance, autonomy, practical application, prior experience. |

Instructional design is commonly described as the practice of creating effective learning experiences using models, theories, and strategies, with the goal of improving understanding, retention, and performance. (ATD) Common instructional design frameworks include ADDIE, Merrill’s Principles, Gagné’s Nine Events, and Bloom’s Taxonomy. (shiftelearning.com)

## A useful distinction

For documentation, I’d separate the knowledge into three layers:

| Layer | Name | Example |
| --- | --- | --- |
| 1 | **Subject/domain knowledge** | How the product, API, machine, business process, or technology works. |
| 2 | **Communication knowledge** | How to explain it clearly, accurately, and appropriately. |
| 3 | **Learning/design knowledge** | How to structure the material so the reader can become capable, not just informed. |
